# Thaqqa

## 簡易説明

複雑な処理を必要とする文字をレンダリングするシステムをバックエンドとして実装したもの。
元はjavascriptやtypescriptによる実装を検討していたが、軽量プロセスと高い並行処理性能を持つBEAM上で動作し、保守性と可読性がより高いElixirを選択。
細かい粒度の処理を独立プロセスに分解し、マルチパイプライン的に並列実行することでスループットを改善した。

今後のチーム開発も見据え、段階的に仕様書を書き留めることとしている。
本実装を元としたAPI開発も進めている。

https://qiita.com/asagikaki/items/0bd95438fa0c6339856a
詳しい話はこちらで。

## 概要

本プロジェクトは、架空文字体系を柔軟に定義・描画するレンダリングエンジンです。
固定ロジックではなく、DSL（ドメイン固有言語）によって文字構造を定義可能とし、拡張性と再利用性を重視して設計しています。

### 背景・目的

　従来の実装では、特定のアルファベット体系に依存した条件分岐により文字を描画していました。
　しかしこの方法では以下の問題がありました：

・新しい文字体系を追加するたびにコード修正が必要
・ロジックが肥大化し保守性が低下
・汎用的な文字生成エンジンとして再利用できない

これらの課題を解決するため、文字構造をデータとして扱う設計への転換を行いました。

## 主な特徴
・ベクター的な描画処理
・DSLによる文字構造定義
・拡張性の高い設計（新規文字体系、新処理をコード変更なしで追加可能）
・並列処理を考慮したレンダリング設計
・技術構成
・言語：Elixir（最終実装）
・初期実装：JavaScript
・中間検証：Rust
・設計の変遷と改善

1. 条件分岐ベース設計 → DSL設計への移行

課題
初期実装では、固定アルファベットに対する条件分岐で描画処理を記述していた。

問題点

拡張性が低い
文字体系の追加ごとにコード変更が必要

改善

DSLを設計し、文字構造をデータとして定義できるように変更

結果

新規文字体系の追加が容易に
コード変更なしで拡張可能な設計を実現

2. 技術選定の見直し（JS → Rust → Elixir）

課題

・JavaScriptでは処理速度・構造面に限界

試行

・Rustへ移行しパフォーマンス改善を試みた

問題点

・開発効率が低下
・設計変更の柔軟性が不足

最終判断

・Elixirに移行

理由

・並列処理との相性
・データ中心設計との親和性
・記述の柔軟性

結果

・開発効率と構造のバランスが最適化


3. データ構造の見直し

課題

・関数ベースで値を取得・生成する設計

問題点

・オーバーヘッドが大きい
・処理の見通しが悪い

改善

・データ構造を直接扱う設計に変更

結果

・パフォーマンス改善
・処理の単純化

4. 並列処理の最適化

課題

・並列化によるパフォーマンス改善を検討

問題点

・タスク分割の粒度によって逆に遅くなるケースが発生

対応

・並列化の粒度を調整
・オーバーヘッドとスループットのバランスを検証

結果

・処理効率の最適化

5. エラー処理の設計

課題
・エラーハンドリングの充実

問題点
・新たなバグが生じた際のデバッグが困難となる恐れ。

対応
・responsible欄を設け第一ドメイン(regex_khhyl/dsl,render/render,fontregistry/fonttable)を明示。
・Thaqqaのライブラリ上ではThaqqa.Errorを分割し、コード上での責務判別性を高めた。


今後の展望

入力インターフェースの改善
描画最適化のさらなる検証
技術的に意識した点
拡張性を最優先とした設計
データ駆動設計への転換
技術選定におけるトレードオフの検証
